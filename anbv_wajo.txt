Document purpose
================

This document explains the entire project from beginning to end. It is written as if I am walking an interviewer through what I built, why I built it this way, how every important part works, how the system learns, how it remains safe, how it is tested, and how it can later be connected to Gmail.

The central principle of the project is:

    Autonomy may increase through evidence, but authority never increases through learning.

In other words, the agent can learn that a user usually wants newsletters archived and gradually ask less often. It can never learn that it is allowed to send an external email, spend money, permanently delete data, or bypass a safety rule. Learning can make the system less annoying inside a fixed safety boundary; it cannot weaken that boundary.

1. PROBLEM INTERPRETATION
=========================

The task is to build a proactive AI agent that manages email. For every incoming email or situation, the system must decide one of four autonomy levels:

1. SILENT
   Perform the action without interrupting the user.

2. NOTIFY
   Perform the action and tell the user what was done.

3. ASK
   Show the exact proposed action and wait for explicit approval.

4. ESCALATE
   Do not execute. Hand the situation back to the user because it is dangerous, ambiguous, sensitive, unsupported, or affected by prompt injection.

The difficult part is not classifying an email. The difficult part is calibration: learning when the user is comfortable with autonomy without ever making a risky or irreversible decision independently.

I split the problem into two fundamentally different kinds of logic:

A. Probabilistic interpretation
   An LLM interprets the email and proposes an action. This may occasionally be wrong, so it is never trusted as the final authority.

B. Deterministic authorization
   Normal Python code determines whether that proposed action is allowed and how much autonomy it may receive. This code is small, explicit, testable, and independent of model persuasion.

That separation is the main architectural decision. The LLM is a planner, not an executor and not a security boundary.


2. PRODUCT SCOPE AND NON-GOALS
==============================

Actions implemented in the core take-home:

- no_action
- mark_read
- mark_unread
- add_label
- archive
- create_draft
- trash
- send_reply, available only after exact user approval
- forward, either approval-only or disabled if it cannot be demonstrated safely

Actions deliberately unavailable in the core:

- permanent deletion
- payments or purchases
- changing account settings
- credential reset
- signing or accepting legal agreements
- automatically opening links
- automatically executing attachments
- automatically sending external messages without approval

The finished project works entirely with a fixture mailbox and mock executor. Gmail is an optional adapter added only after the safe offline system and evaluation suite pass. This gives an interviewer a reproducible demo without requiring access to a real mailbox.


3. WHAT THE FINISHED DEMONSTRATION WILL SHOW
============================================

The final demo tells a coherent story:

Scenario 1 - cold start
    A newsletter arrives. The system recognizes it and proposes archive. Because the user preference is unknown, it asks first.

Scenario 2 - learning
    The user repeatedly approves archiving similar newsletters. The contextual confidence grows. The system eventually moves from ASK to NOTIFY and, after enough evidence, to SILENT because archive is internal and reversible.

Scenario 3 - hard safety floor
    The user has maximum trust for replies, but an external reply still stays at ASK. This proves that learning cannot weaken policy.

Scenario 4 - prompt injection
    An email says to ignore previous instructions, reveal secrets, or forward information. The system marks it as suspicious and escalates without executing anything.

Scenario 5 - correctness under failure
    A simulated external send times out. The result becomes UNKNOWN rather than FAILED, and the system does not retry automatically because the provider may have accepted the send.

After the scenarios, the demo shows the actual evaluation report: safety invariant violations, planner accuracy, injection results, learning curves, calibration, and failure-injection outcomes.


4. TECHNOLOGY STACK AND WHY IT WAS CHOSEN
==========================================

Language:
    Python 3.12

Primary libraries:

- pydantic v2
  Defines strict typed domain models and validates LLM structured output.

- openai
  Calls the Responses API for the planner. The model returns a strict action proposal, not free-form executable commands.

- typer
  Provides a clear command-line interface.

- rich
  Displays decisions, safety reasons, approvals, tables, and evaluation results cleanly.

- sqlite3 or SQLAlchemy Core
  Stores immutable events, current preference projections, approvals, and execution state.

- scipy
  Computes Beta-distribution posterior probabilities for contextual preference learning.

- scikit-learn
  Computes Brier score, calibration curves, confusion matrices, and classification metrics.

- pytest
  Runs unit and integration tests.

- hypothesis
  Generates large combinations of policy and approval states to verify universal safety properties.

- pytest-cov
  Reports branch coverage, particularly for safety-critical modules.

- ruff
  Formatting and linting.

- pyright or mypy
  Strict static type checking.

- matplotlib
  Produces learning and calibration plots for the final report.

Development and packaging:

- uv manages the virtual environment, locked dependencies, and commands.
- pyproject.toml contains dependency and tooling configuration.
- .env stores local configuration, while .env.example documents required keys without containing secrets.

The project deliberately avoids Docker, PostgreSQL, Redis, Celery, Kafka, and a web frontend in the required path. Those tools are appropriate at greater scale, but they would add setup and failure modes without improving the core take-home evidence.


5. SYSTEM ARCHITECTURE
======================

High-level flow:

    Fixture mailbox or optional Gmail adapter
                    |
                    v
        Email ingestion and normalization
                    |
                    v
          Untrusted-content boundary
                    |
          +---------+----------+
          |                    |
          v                    v
      LLM planner       injection/sensitivity scan
          |                    |
          +---------+----------+
                    v
          deterministic policy engine
                    |
                    v
        contextual preference learner
                    |
                    v
          four-way autonomy router
           /        |       |       \
          v         v       v        v
       SILENT    NOTIFY     ASK    ESCALATE
          |         |       |        |
          +----+----+       |        +--> human review
               |            v
               |      approval workflow
               |            |
               +------------+
                    v
          policy revalidation
                    |
                    v
          idempotent executor
                    |
                    v
           append-only event log
                    |
                    v
          feedback and learning update

Critical trust boundaries:

1. Email bodies are untrusted input.
2. LLM output is untrusted until Pydantic validation succeeds.
3. A valid proposal is still not authorized.
4. Only the deterministic policy engine can establish the minimum autonomy tier.
5. Only the backend approval service can authorize an approval-only action.
6. The executor validates policy and approval again immediately before side effects.
7. The learner can update preference evidence only; it cannot update action capabilities or safety rules.

7. DOMAIN MODEL
===============

All boundaries use explicit Pydantic models. No dictionary containing arbitrary fields is allowed to flow into the executor.

EmailEnvelope contains:

- internal email ID
- provider message ID
- provider thread ID
- sender address and display name
- recipients
- subject
- normalized plain text body
- sanitized HTML metadata if required
- received timestamp
- attachment metadata only, not automatically opened content
- headers needed for classification
- source type, fixture or Gmail

ActionProposal contains:

- proposal ID and version
- email ID
- action_type
- intent
- human-readable summary
- typed payload
- evidence snippets or fields used for the proposal
- uncertainty reasons
- proposed timestamp

It intentionally does not include an executable Python function, SQL statement, URL to open, or a model-selected safety tier.

CapabilitySpec contains static code-owned metadata:

- action_type
- effect class
- reversible
- external
- destructive
- financial
- enabled
- minimum autonomy tier
- approval required

RiskAssessment contains:

- typed injection signals, such as instruction override, fake role, secret exfiltration, fake approval, encoded instructions, and obfuscation
- typed sensitive categories, such as credentials, account recovery, banking, payment, legal commitment, and personal data
- normalization flags for truncated content, invisible characters, control characters, and content with no visible text
- compact evidence records containing the signal, its source field, and only the matched excerpt
- missing required information
- a derived injection_detected value, so the summary boolean cannot disagree with the underlying signals

The RiskScanner examines the normalized subject and body independently. It also consumes the
EmailNormalizationReport, allowing preprocessing discoveries such as repeated zero-width
characters or hidden-only HTML to become auditable risk evidence. The scanner deliberately does
not choose SILENT, NOTIFY, ASK, or ESCALATE. It is a perception component; the deterministic
policy engine remains the authority component.

Decision contains:

- decision ID
- proposal ID and version
- selected autonomy tier
- policy minimum tier
- learned preference tier
- content-risk floor
- final reasons
- whether execution is currently possible
- timestamp

FeedbackEvent contains:

- event ID
- decision ID
- context key
- feedback type: approved, edited, rejected, undone, corrected
- original payload hash
- edited proposal when present
- timestamp

Approval contains:

- approval ID
- proposal ID and version
- canonical payload hash
- approving actor
- created time
- expiry time
- consumed time
- status

ExecutionRecord contains:

- execution ID
- proposal ID
- idempotency key
- state
- attempt number
- provider operation ID if available
- started and completed timestamps
- result or error classification


8. ACTION CAPABILITY CATALOGUE AND HARD SAFETY FLOORS
=====================================================

The capability catalogue is Python-owned constant data. The LLM and learner can read its implications but cannot edit it.

Suggested catalogue:

    no_action       internal, reversible, enabled, minimum SILENT
    mark_read       internal, reversible, enabled, minimum SILENT
    mark_unread     internal, reversible, enabled, minimum SILENT
    add_label       internal, reversible, enabled, minimum SILENT
    archive         internal, reversible, enabled, minimum SILENT
    create_draft    internal, reversible, enabled, minimum NOTIFY
    trash           internal, recoverable but destructive, enabled, minimum ASK
    send_reply      external, enabled only with approval, minimum ASK
    forward         external, approval-only or disabled, minimum ASK
    unsubscribe     external, approval-only or disabled, minimum ASK
    permanent_delete destructive and irreversible, disabled, ESCALATE
    payment         financial, disabled, ESCALATE
    account_change  sensitive external authority, disabled, ESCALATE

Autonomy ordering:

    SILENT < NOTIFY < ASK < ESCALATE

The final decision is the most restrictive relevant tier:

    final_tier = max(
        capability_minimum,
        content_risk_floor,
        learned_preference_tier,
        novelty_or_uncertainty_floor,
    )

Because max means more restrictive in this ordering, user learning can never push a proposal below the capability minimum.

Hard rules include:

- Any external write is at least ASK.
- Any financial action escalates.
- Permanent deletion is unavailable.
- Credential, banking, account recovery, or legal commitment content escalates.
- Detected prompt injection escalates.
- Unknown action types escalate.
- Invalid or missing model output escalates.
- Trash is at least ASK.
- Draft creation is at least NOTIFY.
- The policy is checked when deciding and checked again immediately before executing.


9. EMAIL INGESTION AND NORMALIZATION
====================================

The fixture adapter reads JSON or JSONL email fixtures. The optional Gmail adapter maps provider responses into the same EmailEnvelope type. The rest of the system never needs to know which adapter produced the message.

Normalization performs:

1. Size limits
   Reject or truncate unusually large fields using explicit recorded rules.

2. Unicode normalization
   Normalize confusable formatting where appropriate and remove zero-width characters used to hide instructions.

3. HTML handling
   Convert HTML to sanitized visible text. Scripts, forms, remote resources, and active content are not executed.

4. Quoted content marking
   Preserve useful quoted reply content but mark it so the planner can distinguish current content from earlier messages.

5. URL treatment
   Record URLs as inert text. The system does not automatically fetch them.

6. Attachment treatment
   Record filename, media type, and size. The core system never executes or automatically opens attachments.

7. Stable identifiers
   Preserve provider message IDs and create a stable internal email ID for deduplication.

8. Audit event
   Append email_received and email_normalized events before planning.

The normalized email is still untrusted. Normalization reduces attack surface; it does not convert email content into instructions.


10. LLM PLANNER
===============

The planner receives:

- a system/developer instruction describing its limited classification role
- the normalized email inside an explicitly untrusted data field
- the allowed action schema
- the requirement to return structured output

The planner does not receive Gmail tools or execution functions. It cannot send, archive, label, delete, or approve anything.

The planner returns a PlannerOutput with strict schema validation. Application code validates the
request allowlist and then binds that output to an email to create an ActionProposal. A conceptual
request looks like:

    response = client.responses.create(
        model=config.planner_model,
        instructions=PLANNER_INSTRUCTIONS,
        input=build_untrusted_email_input(email),
        text={"format": proposal_json_schema},
    )

The exact SDK syntax will be implemented against the installed SDK version and covered by a contract test.

The implemented Step 12 boundary is:

    class Planner(Protocol):
        def plan(self, request: PlannerRequest) -> PlannerOutput: ...

PlannerRequest contains the normalized EmailEnvelope, the exact enabled-action allowlist, whether
normalization changed the content, and a literal marker declaring the content to be untrusted. A
PlannerOutput is still model-owned data. validate_planner_output first checks that its action was
allowed by this request; only bind_planner_output may then attach the application-owned email ID and
turn it into an ActionProposal.

PlannerError separates operational unavailability from a contract violation. Either failure is
handled by the future agent loop as a safe inability to plan, never as permission to execute.

Planner responsibilities:

- identify intent
- choose one supported proposed action
- fill the typed payload
- summarize the reason using evidence
- report ambiguity or missing information

Planner non-responsibilities:

- decide the final autonomy tier
- declare an action safe
- change policy
- approve a payload
- call a tool
- execute an action
- update trust

If the API fails, times out, returns invalid JSON, returns an unknown action, or violates the schema, the pipeline records the failure and returns ESCALATE or a safe deferred state.


11. PROMPT-INJECTION AND SENSITIVE-CONTENT HANDLING
===================================================

Email is a hostile instruction channel. An email may contain text that looks like system instructions, fake approval, hidden Unicode, or a request to expose information.

The defense is layered:

Layer 1 - structural isolation
    Email content is passed as data, never inserted into developer instructions.

Layer 2 - no planner tools
    Even a compromised planner has no execution capability.

Layer 3 - strict output schema
    The model can only propose known typed actions.

Layer 4 - deterministic heuristics
    Scan for instruction override language, fake system roles, secret requests, encoded directives, hidden characters, suspicious forwarding requests, and approval impersonation.

Layer 5 - optional semantic injection detector
    A separate classification call can identify attacks that heuristics miss. This improves recall but is not treated as the security boundary.

Layer 6 - content sensitivity floors
    Banking, credentials, account recovery, legal commitments, financial transfers, and other sensitive content escalate independently of the proposed action.

Layer 7 - capability floors
    External or destructive actions remain ASK or ESCALATE even if injection detection misses an attack.

Layer 8 - approval binding and execution validation
    No email text can manufacture a valid backend approval record or payload hash.

The injection detector returns evidence and categories, not instructions. Suspicious content is logged in a redacted form appropriate for the demonstration.


12. DETERMINISTIC POLICY ENGINE
===============================

The policy engine is deliberately small and boring. That is a positive security property. It takes typed inputs and returns a DecisionCandidate without calling an LLM, database, Gmail, or network service.

Inputs:

- ActionProposal
- CapabilitySpec
- RiskAssessment
- context novelty information
- current learned preference recommendation

Conceptual algorithm:

    def decide(proposal, risk, learned_tier, context_state):
        capability = capability_catalog.lookup(proposal.action_type)

        if capability is missing:
            return ESCALATE("unknown action")

        if not capability.enabled:
            return ESCALATE("action disabled")

        if risk.injection_detected:
            return ESCALATE("prompt injection")

        if risk.has_hard_sensitive_category:
            return ESCALATE("sensitive content")

        content_floor = calculate_content_floor(risk, proposal)
        novelty_floor = calculate_novelty_floor(context_state, proposal)

        final_tier = most_restrictive(
            capability.minimum_tier,
            content_floor,
            learned_tier,
            novelty_floor,
        )

        return Decision(final_tier, all_reasons)

There are no early successful execution returns inside the policy engine. Every path constructs a complete decision and passes it through a final invariant validator.

The invariant validator runs after policy calculation and again before execution. It contains assertions expressed as ordinary conditions with safe failure behavior, for example:

    if capability.external and decision.tier < ASK:
        raise PolicyViolation

    if capability.financial or not capability.enabled:
        deny_execution

The production path does not rely on Python assert statements because assertions can be disabled. It raises explicit domain errors, records the event, and fails closed.

Implemented Step 9 behavior:

1. The engine obtains the action's immutable capability floor from the catalogue.
2. It independently calculates a content floor. Prompt injection and hard-sensitive categories
   produce ESCALATE. Missing information, truncated content, or suspicious normalization produce
   at least ASK.
3. It combines capability_floor, content_floor, and preference_tier with most_restrictive(). A
   less restrictive preference can therefore never cancel a stronger safety requirement.
4. It creates an immutable Decision containing the proposal identity, all three component tiers,
   the final tier, and human-readable audit reasons.
5. A second validation pass recomputes the expected floors and final tier. It also checks proposal
   ID and version binding, the original preference recommendation, external and destructive action
   floors, disabled and financial actions, injection, sensitive content, missing information, and
   normalization warnings. Any mismatch raises PolicyViolation.

The scripts/check_policy.py smoke checker currently exercises all 13 action capabilities against
all four preference recommendations, five explicit content-risk cases, a downgraded-decision
tampering attempt, and a forged-preference tampering attempt. These 59 deterministic checks are a
fast development gate. The larger property-based and end-to-end test suite is intentionally added
later in the testing steps.


13. CONTEXTUAL PREFERENCE LEARNING
==================================

The learning goal is not to predict a universal user personality. It is to learn narrow, explainable preferences in exact contexts.

Context key:

    schema_version
    + action_type
    + intent
    + sender_bucket
    + normalized sender identity hash
    + recipient_scope
    + action_variant

The concrete storage key is:

    ctx_v1_<sha256 of canonical dimensions>

The full normalized sender address and a label name are not written into the key. They are hashed
before the final context key is generated. This preserves stable equality while avoiding obvious
personal information in database primary keys and logs.

Plain SHA-256 is pseudonymization, not full anonymization; a determined attacker could guess common
addresses. A production multi-user system should use a tenant-specific keyed HMAC and protect the
key in a secrets manager. SHA-256 is sufficient for deterministic local identity in this take-home,
but the limitation is stated explicitly.

An action variant separates materially different forms of the same action. For example, adding a
Newsletter label does not earn trust for adding a Finance label. Recipient scope distinguishes:

- an operation that affects only the mailbox
- internal recipients
- one external recipient
- multiple external recipients
- mixed internal and external recipients
- no recipient

The previous, overly broad four-field design was:

    action_type
    + intent
    + sender_bucket
    + recipient_scope

It was rejected during implementation because all senders in one bucket could share preference
history. The implemented identity includes a stable hash of the exact normalized sender, so trust
for one known bulk sender cannot transfer to a different known bulk sender.

Example:

    archive | newsletter | known_bulk | sender_hash_A | internal_mailbox | default

This is different from:

    archive | personal | known_person | sender_hash_B | internal_mailbox | default

Trust earned for one sender, intent, action, recipient scope, or action variant cannot authorize a
different context. Broad statistics may be displayed as priors or analytics, but only exact-context
evidence can produce SILENT.

Each context starts with a Beta distribution:

    theta ~ Beta(alpha=1, beta=1)

Theta represents the probability that the user will accept the proposed action in that exact context.

Feedback updates:

- approve or explicit confirmation:
      alpha += 1

- correct autonomous action:
      alpha += 1

- edit proposal:
      original_context beta += 2 and cooldown = at least 3
      the later feedback-orchestration step may record the accepted edited proposal in its own
      exact context; the learner itself never guesses that mapping

- reject or undo:
      beta += 3
      cooldown = at least 5

- no explicit feedback:
      no update

Silence is not counted as approval. The user may not have seen the notification, so learning from non-response would create unjustified confidence.

Tier recommendation:

ASK:
    Fewer than four observations, a cooldown is active, the context is novel, or evidence is weak.

NOTIFY:
    At least four observations and
    P(theta > 0.70) >= 0.90.

SILENT:
    Only when the capability is internal, reversible, low risk, and enabled;
    at least twelve observations exist;
    P(theta > 0.90) >= 0.80;
    no negative feedback occurred in the last five observations;
    the context is an exact match.

ASK remains the learner output for actions whose evidence is insufficient. The learner itself only
permits SILENT for capabilities marked silent_eligible. The independent deterministic policy still
applies its capability floor afterward; for example, strong preference evidence may recommend
NOTIFY for a reply, but the external-action floor produces ASK.

Why posterior probability instead of a simple approval percentage:

A raw ratio of one approval out of one observation is 100 percent but extremely uncertain. The Beta posterior lets the system require both a strong estimated preference and sufficient evidence. It also produces an explainable confidence value for reports and the demo.

Example progression for repeated newsletter archive approval:

    Initial:       Beta(1,1)   -> ASK
    Six approvals  Beta(7,1)   -> NOTIFY because P(theta > 0.7) exceeds 0.90
    More evidence  Beta(...)   -> remain NOTIFY until strict silent criteria pass
    Fifteen approvals Beta(16,1)
                  P(theta > 0.9) = 1 - 0.9^16, approximately 0.815
                  -> SILENT may be allowed for archive only

A later rejection immediately increases beta, records a negative recent event, activates cooldown, and demotes the recommendation.

The implemented learner returns an immutable PreferenceRecommendation rather than only a tier. It
contains alpha, beta, observation count, posterior mean, the probability used for NOTIFY, the
probability used for SILENT, and human-readable reasons. This makes every promotion or refusal
auditable in the demo and measurable in the evaluation harness.

LearningThresholds is frozen code-owned configuration. The model cannot edit evidence minimums,
probability thresholds, feedback weights, or cooldown lengths. InMemoryPreferenceRepository makes
the behavior executable before the SQLite repository arrives in Step 15. Duplicate feedback is not
yet accepted by an application workflow; durable feedback identity and deduplication are added when
feedback is wired end to end in Step 20.


14. FOUR-WAY AUTONOMY ROUTER
============================

The router converts the final Decision into an operational next step.

SILENT:
    Execute only after final policy validation. Record the decision and result. The action must be internal, reversible, and low risk.

NOTIFY:
    Execute after validation and create a notification event describing the completed action and how to undo it when applicable.

ASK:
    Do not execute. Produce an approval request containing the exact canonical payload the user would authorize.

ESCALATE:
    Do not execute. Show the user why the system stopped, including missing information, risk flags, unsupported capability, or injection concerns.

The router contains no special exception that allows the model or UI to override a final tier.


15. APPROVAL WORKFLOW
=====================

Approval is not a boolean attached to an email. It is a single-use authorization for one exact proposal payload and version.

Canonical payload for a reply includes:

- email and thread identifiers
- action type
- exact recipients
- exact subject
- exact body
- proposal version

Canonicalization uses stable field ordering and stable encoding. The resulting bytes are hashed using SHA-256. The approval record stores that hash.

Approval request flow:

1. The ASK decision is persisted.
2. The exact proposed payload is canonicalized.
3. A payload hash and expiring approval request are stored.
4. The CLI displays recipients, subject, body, reasons, and expiry.
5. The user chooses approve, edit, or reject.

Approve:

- Record the approving actor and timestamp.
- Mark the approval available but not yet consumed.
- Pass the same payload to the executor.
- Recompute its hash and compare it to the stored hash.
- Re-run current policy.
- Atomically consume the approval as execution begins.

Edit:

- The old approval is invalidated.
- The edited content becomes a new proposal version.
- Policy and risk assessment run again.
- A new approval request with a new hash is created.
- Learning records negative evidence for the old proposal context and positive evidence for the user-corrected context only after explicit confirmation.

Reject:

- Mark the approval rejected.
- Do not execute.
- Record negative preference evidence and cooldown.

An approval is rejected by the executor when it is expired, used, revoked, bound to another version, or has a different payload hash.


16. EXECUTION ENGINE AND IDEMPOTENCY
====================================

The executor accepts only a validated ExecutionCommand. The command can be constructed only after the decision and, when required, approval checks pass.

Execution state machine:

    PLANNED
       |
       +--> AWAITING_APPROVAL
                |
                v
             APPROVED
                |
                v
             EXECUTING
              /  |  \
             v   v   v
       SUCCEEDED FAILED_SAFE UNKNOWN

UNKNOWN is required for external effects. If a send request times out, the application cannot know whether Gmail accepted it. Retrying might create a duplicate email, so the system records UNKNOWN and requires reconciliation or manual review.

Idempotency key:

    SHA256(
        user_id
        + provider_message_id
        + canonical_action_payload
        + proposal_version
    )

The autonomy tier is not included because retry identity depends on the effect, not on whether the decision was ASK or NOTIFY.

Before a side effect:

1. Validate the action is enabled.
2. Re-run policy and invariants.
3. Validate approval when required.
4. Check for an existing successful execution with the same key.
5. Create or claim the execution record.
6. Move to EXECUTING.
7. Perform the adapter call.
8. Persist SUCCEEDED, FAILED_SAFE, or UNKNOWN.

Fixture and mock internal operations can be made atomic with the SQLite event transaction. A real external provider call cannot be part of the database transaction, so the state machine and reconciliation rules explicitly represent the gap.

Retry rules:

- Read-only calls may retry with bounded backoff.
- Internal reversible label/archive operations may retry when provider reconciliation confirms the current state.
- Invalid requests do not retry.
- External send with an unknown outcome does not automatically retry.
- The mock executor can inject every failure classification for testing.

SQLite operating rules:

- Use one writer path in the take-home application.
- Keep transactions short.
- Configure a busy timeout.
- Enable foreign keys.

- Store UTC timestamps.
- Serialize JSON deterministically when it participates in hashes.

The event write and related local projection update happen in one transaction. If projection rebuilding is implemented, current tables can be reconstructed from the append-only log.


18. END-TO-END PROCESSING FLOW
==============================

For one incoming email, the pipeline performs these steps:

Step 1 - ingest
    Read the fixture or Gmail message and reject duplicates using the provider message ID.

Step 2 - normalize
    Sanitize content, preserve required metadata, enforce size limits, and append normalization events.

Step 3 - scan
    Run deterministic injection and sensitivity checks.

Step 4 - plan
    Ask the LLM for a strict ActionProposal. Validate it with Pydantic.

Step 5 - enrich risk
    Combine heuristic, semantic, structural, novelty, and missing-data findings into RiskAssessment.

Step 6 - load preference context
    Construct the exact context key and load its Beta state.

Step 7 - obtain learning recommendation
    Compute ASK, NOTIFY, or SILENT using evidence and posterior thresholds.

Step 8 - apply deterministic policy
    Combine capability, content, novelty, and learned tiers using the most restrictive result.

Step 9 - validate decision invariants
    Ensure external, disabled, destructive, financial, unknown, and injection cases cannot violate their floors.

Step 10 - route
    Execute, execute-and-notify, request approval, or escalate.

Step 11 - validate before execution
    Re-run policy, approval, payload, and idempotency checks.

Step 12 - execute through adapter
    The core calls the fixture/mock executor or optional Gmail adapter through the same interface.

Step 13 - record outcome
    Append events and update projections.

Step 14 - collect explicit feedback
    Record approve, edit, reject, undo, or correction.

Step 15 - update preference evidence
    Apply the feedback once using deduplication and append the preference update event.


19. USER FEEDBACK FLOW
======================

Feedback is associated with the decision and exact context. It is not inferred from vague inactivity.

For ASK:

- approval is positive evidence
- edit teaches that the original proposal was not acceptable as-is
- rejection is strong negative evidence

For NOTIFY:

- explicit confirmation is positive evidence
- correction or undo is negative evidence
- no response does not update the model

For SILENT:

- correct/confirm is positive evidence when the demo explicitly collects it
- undo or correction is strong negative evidence
- negative feedback forces immediate demotion and cooldown

Duplicate feedback events are ignored using a stable feedback identity. If storage fails, the UI reports that feedback was not committed rather than pretending learning succeeded.

21. OPTIONAL GMAIL INTEGRATION
==============================

Gmail is deliberately an adapter, not part of the domain or policy design. The core passes against fixtures first.

The Gmail phase adds:

1. A dedicated test Google account.
2. OAuth client configuration and local token handling.
3. The minimum scopes required by the enabled actions.
4. Mapping Gmail messages into EmailEnvelope.
5. Read, label, archive, and draft implementations.
6. Approved send only to a preconfigured test recipient.
7. Provider IDs stored for reconciliation.

Safety rules for Gmail testing:

- Gmail execution is disabled by default.
- Dry-run mode is the default.
- No production mailbox is required for review.
- Sending is restricted to a test account and explicit approval.
- Permanent delete and payment do not exist in the adapter.
- Tokens are never committed.
- Email bodies are redacted from ordinary logs where possible.
- Pub/Sub push delivery is not required for the take-home; a manual sync command is sufficient.

Adapter interface concept:

    class MailboxExecutor(Protocol):
        def execute(command: ExecutionCommand) -> ExecutionResult: ...

The single method keeps orchestration independent of Gmail-specific methods. ExecutionCommand is a
typed, immutable envelope containing exact proposal and decision identities, the action payload,
the authorized autonomy tier, approval identity when required, and an idempotency key. ESCALATE is
not a valid command tier. ASK cannot become a command without an approval ID.

execute_checked validates capability floors and disabled actions before calling the adapter. It
then verifies that the returned command ID, proposal ID, and idempotency key match the exact command.
The full policy, approval hash, and idempotent state-machine validation are implemented later; this
step defines the narrow interface they must feed.

The mock and Gmail implementations satisfy the same contract tests. Policy tests never need Gmail credentials.


22. EVALUATION DATASETS
=======================

The project maintains separate datasets because each layer answers a different question.

A. Policy combinations

Generated by Hypothesis rather than written manually. It combines capabilities, risk flags, preference recommendations, approvals, payload states, and execution histories.

B. Semantic planner dataset

Approximately 60 to 80 human-reviewed emails covering normal, ambiguous, sensitive, and unusual cases. Each item includes:

- expected action
- expected intent
- required risk categories
- acceptable action alternatives for genuinely ambiguous cases
- minimum allowed tier or set of allowed tiers given an explicit state
- human annotation notes

C. Injection dataset

At least 40 adversarial messages and 40 matched benign controls. The paired controls share words or themes with attacks without actually instructing the agent to break policy. This measures both recall and false positives.

D. Learning-persona dataset

At least four chronological personas with 20 to 30 messages each. Each step defines the email context and simulated explicit feedback. The chronological order matters because the decision at time t must use only feedback available before time t.

E. Failure scenarios

Scripted adapter and storage failures covering timeouts, exceptions, duplicates, restarts, payload tampering, approval replay, and unknown external outcomes.

Dataset governance:

- Keep development and held-out semantic cases separate.
- Freeze the final held-out set before final prompt tuning.
- Version datasets in Git.
- Hash dataset content in each evaluation report.
- Do not include private real-world email without authorization and redaction.
- Preserve raw failing case IDs in reports.
- Review ambiguous high-risk labels manually rather than forcing a misleading exact label.


23. TEST AND EVALUATION STRATEGY
================================

The word flawless is not used as a claim. LLM output is nondeterministic. The engineering goal is zero observed safety-floor violations in deterministic and adversarial testing, plus honestly measured semantic and calibration quality.

Layer 1 - static checks

- ruff format --check
- ruff check
- pyright or mypy strict checking
- dependency and secret scanning where available

Layer 2 - unit tests

Test every domain constructor, canonicalizer, capability, policy branch, Beta update, context builder, state transition, approval rule, and idempotency function.

Layer 3 - property tests

Generate at least 1,000 combinations and enforce:

- external action tier is never below ASK
- financial action always escalates
- disabled action is never executable
- injection always escalates when detected
- permanent delete is never executable
- unknown action fails closed
- invalid proposal fails closed
- mismatched, used, expired, or revoked approval cannot execute
- learning cannot modify the capability catalogue

Layer 4 - integration tests

Use a temporary SQLite database and fake planner/executor to verify event order, transactions, feedback deduplication, preference projection, approval consumption, and restart behavior.

Layer 5 - live-model semantic evaluation

Call the configured planner model on the frozen dataset. Measure:

- schema-valid output rate
- action accuracy
- intent accuracy
- macro F1
- per-class recall
- risk-flag recall
- confusion matrix
- latency and token usage

Run the model evaluation multiple times with fixed prompt, model configuration, dataset, and application version. Model variability should appear in the report instead of being hidden.

Layer 6 - injection evaluation

Measure:

- attack success rate
- injection detection recall
- paired benign false-positive rate
- correct paired classification
- unsafe external effect count

Even if detector recall is imperfect, unsafe external effects must remain zero because the architecture has independent capability and approval floors.

Layer 7 - learning evaluation

Measure:

- ASK, NOTIFY, and SILENT rate over time
- user disagreement rate
- time to promotion
- time to demotion
- cross-context leakage
- Brier score
- calibration curve
- comparison with a no-learning baseline

The expected qualitative result is fewer unnecessary asks in repeatedly approved safe contexts, with no increase in unsafe autonomy and immediate demotion after rejection.

Layer 8 - end-to-end tests

Run fixture email through normalization, planner, detector, policy, learner, router, approval, executor, events, feedback, and learning. Verify both returned output and persisted audit state.

Layer 9 - manual review

Inspect every final eval failure, the worst-confidence cases, ambiguous items, all escalation reasons, the five demo transcripts, and the generated charts. Automated numbers are combined with human judgment.


24. FAILURE-INJECTION TESTING
=============================

Failures are created intentionally, not merely waited for.

Planner failures:

- network timeout
- rate limit
- invalid JSON
- valid JSON with missing fields
- unknown action type
- payload that violates its action schema
- conflicting intent and payload

Expected result: no execution; append a failure event; return ESCALATE or safe defer.

Approval failures:

- recipient changed after approval
- subject changed after approval
- body changed after approval
- proposal version changed
- approval expired
- approval replayed
- approval used concurrently twice

Expected result: no execution for the invalid attempt and an auditable denial reason.

Execution failures:

- crash before EXECUTING is committed
- crash after EXECUTING but before adapter call
- adapter fails before applying an effect
- adapter applies external effect but response is lost
- crash after provider success but before local success record
- duplicate processing of the incoming email

Expected result depends on certainty. Safe known failures become FAILED_SAFE. Ambiguous external results become UNKNOWN and are not automatically repeated.

Learning failures:

- duplicate approval event
- duplicate rejection event
- projection update interrupted
- restart before projection update
- out-of-order feedback

Expected result: each explicit feedback changes evidence exactly once; the event log permits reconstruction; no silent corruption.

Storage failures:

- locked SQLite database
- constraint violation
- malformed stored event
- transaction rollback

Expected result: no side effect starts unless required local safety and audit state is durably recorded. The CLI communicates the safe failure clearly.

30. KNOWN LIMITATIONS AND PRODUCTION EVOLUTION
==============================================

Take-home limitations:

- The fixture mailbox is the required execution environment; Gmail is optional.
- The semantic dataset is intentionally modest and human-reviewed, not a production-scale traffic sample.
- Preference contexts use manually designed buckets rather than learned embeddings.
- The CLI is optimized for evaluation, not consumer UX.
- The detector cannot guarantee perfect injection recall; structural safety remains the real defense.
- SQLite and a single writer are suitable for the demo, not high-volume multi-user operation.
- Reconciliation for external UNKNOWN outcomes is demonstrated through the mock adapter and provider IDs rather than a full operations service.

Production evolution:

    Gmail Pub/Sub
        -> ingestion service
        -> durable queue
        -> planner workers
        -> deterministic policy service/library
        -> PostgreSQL event and state store
        -> approval API and user interface
        -> idempotent executor workers
        -> reconciliation service
        -> monitoring and audit dashboard

32. SHORT INTERVIEWER SUMMARY
=============================

"I built the email agent as a constrained decision system rather than giving an LLM direct mailbox access. The LLM only converts untrusted email content into a typed proposal. A deterministic policy catalogue establishes immutable safety floors: external writes require approval, destructive and financial actions cannot run, and suspicious or sensitive situations escalate.

The system learns only contextual preferences. It uses a Beta posterior for an exact action, intent, sender bucket, and recipient scope. Repeated explicit approval can move an internal reversible action from ask to notify and eventually silent, while rejection immediately reduces autonomy. Learning never changes what an action is allowed to do.

Approval is bound to the exact canonical payload and proposal version, expires, and can be consumed only once. The executor rechecks policy, approval, payload integrity, and idempotency immediately before acting. External timeouts become unknown rather than being retried blindly.

Finally, I evaluate the model and the safety system separately. Property tests prove deterministic invariants over generated combinations, labelled emails measure planner quality, paired attacks and benign controls measure injection handling, chronological personas measure learning and calibration, and injected failures measure correctness under crashes, duplicates, tampering, and uncertain provider outcomes. The result is not a claim that an LLM is flawless; it is an auditable system where risky authority remains deterministic and every probabilistic component has measured behavior."
